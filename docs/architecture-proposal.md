# 웹 에이전시 사무실 — 아키텍처 제안

상태: 사용자 방향 확인 전 제안. 구현 완료 문서 아님.

## 목표와 결정할 사항
사용자가 사무실에 업무를 지시하면 담당 직원이 Claude Code/Codex를 통해 조사·기획·개발·검수하고, 진행과 결과를 공간 속에서 확인한다.

질문 1: 개인 PC에서 실제 작업하는 사무실 / 다중 사용자 서비스 / 시각 데모 중 무엇을 우선할 것인가?
질문 2: 고급 3D + 귀여운 캐릭터 / 고정 시점 2.5D / 현실적인 인물의 3D 중 무엇인가?

추천 초안은 개인용 로컬 실행 + 고급 3D 공간 + 독창적인 귀여운 캐릭터다. 답변 전 해당 방식의 제품 코드는 작성하지 않는다.

## 공간과 아트 방향
- 잠정명: BSD AGENCY OFFICE. 명칭은 변경 가능한 설정으로 둔다.
- 웜 화이트, 월넛, 무광 금속, 청록 포인트. 넓은 창과 도시 야경, 절제된 간접 조명.
- 입구/접수 → 중앙 프로젝트 테이블 → 개발 스튜디오 → 디자인 존 → 유리 회의실 → 검수실 → 라운지.
- 장식 밀도를 낮춰 통로와 업무 구역을 읽기 쉽게 한다.
- 전체 보기에서는 직교 카메라, 직원 선택 시 부드러운 근접 이동. 업무 패널이 열릴 때 선택한 직원이 가려지지 않게 구성한다.
- 이름표와 말풍선은 선택 직원 및 중요한 사건을 우선 표시한다.
- 초기 팀: 운영 매니저, 기획자, 디자이너, 프런트엔드 개발자, 백엔드 개발자, QA. 역할 수와 동시 모델 실행 수는 분리한다.
- 캐릭터 시트: 같은 비율의 정면/측면/후면, 역할별 의상/색, 표정, 손·발 규격. 기존 연예인·마스코트 대신 새 캐릭터를 설계한다.
- 시트는 외형 기준이며 곧바로 움직이는 3D 모델이 되는 것은 아니다. 모델링·리깅·동작 제작을 별도 단계로 둔다.

## 자연스러운 동작
대기 → 목적지 바라보기 → 방향 전환 → 걷기 → 감속 → 자리 정렬 → 앉기 → 타이핑/읽기 → 일어서기 순서를 상태로 관리한다.

3D 선택 시 GLB 스켈레탈 애니메이션과 Three.js 애니메이션 블렌딩을 사용한다. 이동 속도와 보행 주기를 맞추고 좌석 앵커, 손의 책상 위치, 발 접지를 조정한다. 통로 경로 탐색, 장애물 회피, 좌석 예약으로 겹침을 막는다. 말하는 동안 시선·고개·손동작을 약하게 섞는다.

업무 상태와 공간 상태를 구분한다. 실제 도구 실행 중이라고 무조건 걸어 다니게 하지 않는다. 조사 중에는 읽기, 작성 중에는 타이핑, 검수 요청 시 검수 구역 이동, 승인 대기 시 대기 표시를 사용한다. 장식 동작은 실행 완료를 발생시키지 않는다.

## 논리 구조
```text
브라우저: 사무실 렌더러 + 지시창 + 직원/프로젝트/결과 패널
             ↕ HTTP 명령 / SSE 작업 이벤트
로컬 서버: 프로젝트 · 업무 큐 · 권한 · 승인 · 이벤트 저장
             ↕ 검증된 실행 계약
실행기: Claude Code 어댑터 / Codex 어댑터
             ↕ 허용된 프로젝트 작업 공간
파일 변경 · 테스트 · 미리보기 · 결과물
```

- Next.js 15/TypeScript: 화면, 패널, 프로젝트 API. 3D 영역은 클라이언트 전용으로 분리한다.
- Three.js/React Three Fiber: 3D 선택 시의 제안. 2.5D 선택 시 정적 배경+스프라이트 방식으로 교체한다.
- Node 로컬 실행기: 장시간 CLI 프로세스와 취소·시간 제한 관리. 브라우저에는 인증 토큰을 보내지 않는다.
- 개인용 저장소 제안: SQLite와 로컬 결과 파일. Supabase는 원격 동기화/다중 사용자 선택 시 도입 여부를 결정한다.
- Vercel/Netlify에 프런트엔드를 배포해도 사용자 PC의 CLI가 자동 연결되지는 않는다. 원격 운영은 별도 인증된 로컬 연결기 설계가 필요하다.
- 초기에는 localhost만 수신하고 Origin 검증과 로컬 세션 인증을 둔다.

```text

src/features/projects/        프로젝트·작업 경로
src/features/tasks/           지시·상태·큐
src/features/approvals/       변경·외부 작업 승인
src/features/artifacts/       결과·미리보기·검증 근거
src/features/activity/        실시간 이벤트·작업 기록
src/components/               공용 UI
src/lib/contracts/            이벤트·명령 스키마
services/runner/providers/    Claude/Codex 어댑터

```

## 작업과 데이터 계약
- Project: id, 이름, 검증한 작업 루트, 허용 도구, 실행 설정.
- Task: id, projectId, roleId, provider, 요청, 상태, 의존 업무, 생성·시작·완료 시간.
- Run: id, taskId, 제공자 세션, 실행 PID, 종료 코드, 취소 상태. 인증 비밀은 저장하지 않는다.
- Event: id, runId, sequence, timestamp, type, 정제한 payload. 중복 방지와 재연결 커서를 제공한다.
- Artifact: id, runId, 작업 루트 안의 상대 경로, 종류, 검증 상태.
- Approval: id, taskId, 대상 작업, 변경 요약, 승인/거절 시각.

업무 상태: queued → running → awaiting_approval/review → succeeded, failed, cancelled. 권한 거절·사용량 제한·연결 끊김은 별도로 표시한다. CLI 종료 코드만으로 검수까지 통과했다고 판단하지 않는다.

하나의 코드 작업 공간에는 동시에 한 명만 쓰도록 잠근다. 병렬 개발이 필요한 경우 별도 Git worktree를 사용하고 통합 검증 단계를 둔다. 이벤트 로그는 순서대로 추가하며 렌더링 프레임마다 DB에 기록하지 않는다.

## 실제 운영 흐름
1. 프로젝트 폴더 선택과 허용 범위 확인.
2. 지시 입력 → 담당자와 검증 기준 제안.
3. 담당 제공자의 실제 실행 → 정제된 이벤트와 현재 상태 전달.
4. 변경/결과 파일 수집 → 다른 역할의 검수 → 브라우저 테스트.
5. 사용자에게 변경 내역과 미리보기 제시.
6. 사용자 규칙에 따른 기존 파일 덮어쓰기·삭제·발송·배포 승인을 별도로 처리.

CLI 권한을 일괄 우회하지 않는다. 초기 쓰기는 새 작업 공간에서 진행하고, 기존 파일 반영은 구체적인 변경 내역에 연결한다. 비대화형 CLI가 승인을 지원하지 않는 경우 승인 필요 상태로 종료한 뒤 범위를 승인받아 재실행한다.

## 단계별 완성 기준
1. 방향 합의: 비주얼·운영 방식·데이터 저장·역할·대표 업무 확정.
2. 하네스: 실패/취소/재연결/권한/동시 쓰기 검증 장치 실행 가능.
3. 수직 시제품: 한 방·한 직원의 걷기/착석/작업과 한 건의 실제 읽기 전용 CLI 작업을 연결.
4. 아트 확정: 캐릭터 시트와 공간의 브라우저 시연 검토.
5. 사무실 확대: 여섯 역할, 업무 배정, 결과물, 검수와 승인 흐름.
6. 검증: 실제 두 CLI 실행 증거, 성능, 반응형, 장애 복구 확인.

사용량 수치가 제공되지 않으면 ‘확인 불가’로 표시한다. 모의 이벤트와 실제 작업 이벤트는 저장소와 화면에서 구별한다.
